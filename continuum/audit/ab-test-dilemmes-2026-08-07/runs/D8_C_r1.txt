B) Statu quo orienté features jusqu'à l'échéance concurrente (variantes : pur features ; features + promesse de migration ultérieure).
C) Migration incrémentale : migrer le module le plus coûteux (~1 mois, 12 des 30 points de maintenance), mesurer, réévaluer (variantes : reste de l'équipe sur les features pendant ce mois ; ou pause complète d'un mois).

6. RISQUES
- A, pire cas : ×2 (8 mois-équipe), le concurrent livre pendant le tunnel, départs en pleine migration. Quasi irréversible une fois engagé. Affectés : équipe entière, clients, direction.
- B, pire cas : les 2 ingénieurs partent en emportant la connaissance du legacy, la maintenance grimpe, et le concurrent livre quand même — double peine. Coût humain élevé, réversibilité moyenne.
- C, pire cas : le mois déborde ou le gain réel est < 12 points ; perte ≈ 1 mois de features, mais leçon apprise tôt et à petit prix. Affectés : roadmap marginalement, équipe faiblement.

7. STRESS-TEST (arguments pour renverser C)
- « La menace concurrente est existentielle et certaine → tout sur les features (B) » : la rumeur n'est que de fiabilité moyenne, et C ne sacrifie qu'~1 mois sur 6 tout en accélérant les 5 suivants. - « L'équipe a besoin d'un geste fort, pas d'un pansement → A » : le pire destructeur de moral est précisément l'enlisement (25 % de ×2) ; C offre une victoire visible en 30 jours.
Aucun argument ne renverse C : sa perte maximale est bornée et il achète exactement l'information qui manque le plus.

8. DÉCISION
Choix : C — migration incrémentale, module le plus coûteux d'abord, le reste de l'équipe restant sur les fonctionnalités.

Si le gain est confirmé, poursuivre par tranches sans jamais geler la livraison de fonctionnalités.
